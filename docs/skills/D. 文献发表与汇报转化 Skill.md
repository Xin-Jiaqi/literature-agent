# 目标

D 用于将 `2-可调用` 中的最终文献笔记转化为外部表达材料，包括知乎文章、小红书正文、朋友圈文字和 Beamer 演讲大纲。

D 不改变 C 的定位。C 仍然是用户自己的低负担、可调用文献笔记；D 才负责公开发布、组会汇报和演讲表达。


**D 默认以已经确认的 C 为科学内容主干。** 除非用户明确要求新增研究、重新推导或核对原文，D 不应重新从 A/B/原始聊天另起一套科学叙事，也不应改变 C 中已经确认的结论层级。D 的主要工作是：重组公开叙事、降低阅读门槛、添加必要过渡、选择图表、处理平台兼容与表达节奏。

【显著note：禁止使用“不是...，而是...”句式！例子："这篇文章最有意思的地方，不只是“预测了一种多铁材料”，而是给出了一套相当清楚的设计逻辑..."——坚决拒绝】

# 输入材料

D 的输入可以包括：

- C 生成的最终可调用文献笔记；
- 原论文 PDF 或关键图表；
- 用户自己的补充理解；
- GoodNotes 摘要或批注；
- 目标平台或汇报场景；
- 是否允许加入用户自己的研究想法。

如果缺少原文、图表、数字来源或关键信息，D 应明确标注“需回原文核对”，不得编造或润色成确定结论。

# 输出模式

D 支持以下输出模式。

## 1. 知乎 / 公众号长文

用于完整展开背景、核心问题、方法或理论、关键结果、意义、限制和个人理解。

输出应适合公开阅读，不应写成文献笔记、FAQ、README 或 PPT 讲稿。

建议结构包括：

- 标题；
- 背景；
- 核心问题；
- 方法或理论思路；
- 关键结果；
- 我的理解或可延伸问题。

### 知乎 / 公众号的表格兼容

知乎和公众号编辑器对“表格内 LaTeX”的支持不稳定，尤其容易直接显示 `\Delta`、`\bar`、`\mathrm`、上下标命令和美元符号。生成知乎或公众号长文时，默认采用一份跨平台兼容稿：

- 正文中的行内公式和独立公式仍可使用 LaTeX；
- **发布用表格默认完全去 LaTeX**：表格单元格内不使用 `$...$`、`\...`、`\mathrm{}`、`\bar{}` 等公式源码，统一改为纯文本、Unicode 或自然语言；
- **表格单元格内禁止出现会被 Markdown 误判为分栏符的裸 `|`**。绝对值写成“Ptot 的绝对值”或 `|Ptot|` 的 Unicode/转义安全形式；bra/ket、集合条件等含竖线表达应移出表格或改写为文字；
- 化学式、上下标、希腊字母、箭头、约等号和单位优先写成 `Ba₃I₆`、`L₁/L₂`、`ΔP`、`→`、`≈`、`μC/cm²` 等形式；
- 空间群和点群尽量写成可读纯文本，例如 `P6₃mc → C6v`、`P-3m1 → D3d`；若 Unicode 无法准确表达上横线，可写成通行的 ASCII 晶体学符号，并在正文首次出现时解释；
- 复杂公式移到表格前后单独展示，表格中只保留变量名、结果和简短物理含义；
- 表格优先控制在 3–4 列。列数过多时拆成两张表，避免知乎网页端和手机端过度拥挤；
- 输出前逐行检查表格：不得残留 LaTeX 源码、未转写的美元符号或会破坏 Markdown 列结构的竖线。

默认只生成这一份跨平台兼容稿，减少重复和后续维护负担。只有用户明确要求保留技术版时，才同时给出：

1. 正常 LaTeX 表格版，用于 Obsidian、论文草稿或支持公式渲染的平台；
2. 纯文本与 Unicode 表格版，用于知乎、公众号及其他公式兼容性较差的平台。

常见转换示例：

- `Ba$_3$I$_6$` → `Ba₃I₆`；
- `$L_1/L_2$` → `L₁/L₂`；
- `$G_{\mathrm{latt}}$` → `Gₗₐₜₜ`；
- `$P6_3mc\rightarrow C_{6v}$` → `P6₃mc → C6v`；
- `$\Delta P\approx52.5\,\mu\mathrm{C/cm^2}$` → `ΔP ≈ 52.5 μC/cm²`。

如果涉及图片，应给出明确的图文占位建议，例如：

- 建议插入 Fig. X；
- 建议裁切哪个 panel；
- 这张图用于说明什么；
- 是否需要打码或去除隐私信息。


图片占位、手动截图、裁切和编辑提醒属于**编辑指令**，必须与可直接发布的正文严格隔离。推荐统一写成 HTML 注释，例如：

    <!-- 【需手动插图】原文 Fig. 2(k–p) + Table I；用于说明同一 stacking 下 P_S 符号基本保持 -->

不要把“建议插图”“请手动打开截图”“这里需要高亮”等对用户的操作说明混进公开正文段落。若平台会显示 HTML 注释，则改为单独的“编辑备注”区，并明确标记为发布前删除。

不需要什么？
- 过多配图建议（最好从原文截取）
- 过于 AI 的语言
	- “不是...，而是...”句式
	- 过多一级标题与过多的编号（类似：十. 栅压为什么可以把信号调节两个数量级？）
	- “图片与版权说明 - 原文图片用于公开文章前，应确认 ACS 的转载许可要求； - 许可不明确时，优先根据原文自行重绘； - 图注中应明确写明论文题目、作者、期刊、年份以及对应原始 Fig./panel； - 自行重绘时使用“据原文改绘”，不要把改绘图表述为原论文原图。” 这种内容。
	- 任何 AI 味重、不符合个人角度叙述的表述方式。
	- 过于啰嗦，一个意思翻来覆去。
- 节标题不要用问句，用简洁的陈述句即可。

## 2. 小红书 / 朋友圈短文

用于高度浓缩研究对象、核心问题、关键方法、代表性结果和推荐阅读理由。

只保留 3–5 个最适合传播的事实亮点，不把知乎文章简单压缩成短文，不堆砌公式、表格和术语。

小红书 / 朋友圈文字应满足：

- 语言自然，但不牺牲准确性；
- 默认用“作者”“研究团队”或“这项工作”等中性称呼；只有用户确实是作者/团队成员，或明确要求相应视角时，才使用“我们”；
- 不使用夸张标题党或营销腔；
- 不把论文摘要压缩成短文；
- 不把理论预测写成实验事实；
- 不把单个材料例子泛化为普遍规律；
- 专业术语第一次出现时应给出简短解释；
- 正文优先控制在 180–420 字。

输出内容可以包括：

- 标题备选；
- 正文；
- 推荐标签；
- 配图建议；
- 需要打码或避免公开的信息。

## 3. Beamer 演讲大纲

用于把最终文献笔记转化为适合口头汇报的 slide 主线。

D 只生成演讲大纲，不直接生成 Beamer `.tex`，也不直接生成逐页完整 slide 内容。因为演讲大纲的核心任务是确定汇报逻辑、听众路径、每页核心句和图表选择，而不是提前进入排版实现。

Beamer 演讲大纲应优先包含：

- 汇报对象；
- 汇报时长；
- 汇报目标；
- 一句话主线；
- slide-by-slide 结构；
- 每页标题；
- 每页核心句；
- 建议使用的图、公式或表格；
- 每页在整场汇报中的作用；
- 哪些内容需要回原文核对。

Beamer 演讲大纲不应写成文献笔记的分页版。每一页都应服务于一个明确的讲述目的。

# Markdown 输出格式

如果可以访问项目文件夹，并且用户要求保存结果，应在用户指定位置新建独立的 D 输出文件，不覆盖 C 的可调用文献笔记；文件名应体现论文和目标平台。**实际文件名必须保留正常空格，不得把空格写成 `%20` 等 URL 编码；下载链接也不要手工把空格替换为 `%20`，应直接引用工具已创建并确认存在的真实文件。**若平台下载层仍可能把 URL 编码写入文件名，可额外提供 ZIP 兼容交付，但 ZIP 内文件名必须保持正常空格。用户未指定保存位置时，先在对话中交付，不随意把发布稿混入文献状态文件夹。若只需在对话中交付可复制内容，默认将最终内容放入一个完整的 Markdown 代码块中，方便一次性复制。

外层使用四反引号：

    ````markdown
    正文内容
    ````

如果用户明确说“不需要代码块”，则直接输出普通 Markdown。

由于 D 可能同时输出知乎文章、小红书正文和 Beamer 演讲大纲，默认不要把三类内容分别放进三个独立代码块。应在同一个 Markdown 代码块中用标题区分，例如：

    # 知乎 / 公众号长文

    ……

    # 小红书 / 朋友圈短文

    ……

    # Beamer 演讲大纲

    ……

外层已经是 Markdown 代码块时，内部不要再使用三反引号代码块。

如果内部需要展示代码、命令或模板片段，统一使用四空格缩进，而不是使用嵌套三反引号。

公式格式遵守 Obsidian Markdown 习惯：

- 行内公式使用 `$...$`；
- 独立公式使用 `$$...$$`；
- **埃单位统一使用 Unicode `Å`，禁止输出 `\AA`**。优先采用 `$E_F=0.3$ V/Å`、`$d=3.0$ Å` 这种“变量/数值在公式内，单位在公式外”的写法；知乎、公众号、小红书、朋友圈和 Obsidian 均按这一规则处理。
- 表格中的 ket / bra 避免直接使用会破坏表格的竖线；
- ket 推荐写为 `$\lvert u_n\rangle$`；
- bra 推荐写为 `$\langle u_n\rvert$`；
- bra-ket 推荐写为 `$\langle u_m \vert u_n \rangle$`。

输出前应检查：

- 外层 Markdown 代码块是否完整闭合；
- 内部是否误用了三反引号代码块；
- 行内公式是否统一使用 `$...$`；
- 独立公式是否统一使用 `$$...$$`；
- 表格中的公式是否包含未处理的竖线 `|`；
- ket / bra 是否使用了不破坏表格的写法；
- 是否出现了 Obsidian 可能不兼容的特殊 LaTeX 命令；
- 全文是否残留 `\AA`；若有，统一替换为 Unicode `Å`，并优先把单位移到公式外；
- 若输出为文件，实际 basename 是否包含 `%20` 或其他 URL 编码片段；若有，应先重命名为正常空格后再交付；
- 若目标为知乎或公众号，表格内是否仍残留 `$...$`、反斜杠命令、未转写的 LaTeX，或单元格内容中的裸 `|`；
- 若表格超过 4 列，是否有必要拆分以适配网页端和手机端；
- 内容是否和当前任务相关，而不是套用旧主题。

# 公开表达原则

D 必须遵守：

- 准确性优先于传播感；
- 不编造材料中没有的结论、数字、应用和比较；
- 不把理论预测写成实验验证；
- 不把单个材料例子泛化成所有材料规律；
- 不把用户自己的理解、质疑或延伸想法写成论文作者结论；
- 公开发布前检查隐私、本地路径、账号、邮箱、手机号、内部数据、审稿意见、私人通信等；
- 使用论文图片时标明论文来源和原始 Fig./panel；公开发布前检查版权或许可条件。许可不明确时，优先自行重绘并注明“据原文改绘”，不要暗示原图属于用户；
- 所有关键数字、图、公式和结论必须能追溯到原文、补充材料或用户明确提供的材料；
- D 中涉及科学内容时，以 C 的已确认结论为默认事实源；不得为了让文章“更完整”而自行重做一套推导。只有用户明确要求新增推导、比较或外部研究时，才新增内容，并在局部标明其来源与证据层级；
- 不确定内容宁可标注“需核对”，不要润色成确定判断。

# 输出取舍原则

D 的目标不是一次性覆盖所有平台，而是根据用户指定目标生成对应材料。

如果用户只要求知乎文章，就只输出知乎文章。

如果用户只要求小红书或朋友圈文字，就只输出短文、标题和标签。

如果用户只要求 Beamer 演讲大纲，就只输出演讲大纲。

如果用户同时要求多个平台，则在同一个 Markdown 代码块中分 section 输出，不使用多个互相独立的代码块。

D 不负责生成最终 Beamer `.tex` 文件，也不负责直接制作 PPT。若用户后续需要制作 Beamer，应先基于 D 生成的演讲大纲，确认主线、图片和每页核心句，再进入单独的排版或模板修改流程。
