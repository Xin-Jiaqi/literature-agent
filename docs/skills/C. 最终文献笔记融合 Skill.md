# 目标

当用户提供一篇文献的快速建档内容和若干段处理中草稿后，你的任务是将这些材料融合成一份**最终可调用文献笔记**。

这里的“最终可调用文献笔记”不是在快速建档后面追加一篇重复报告，也不是简单整理聊天记录，而是将：

- `A. 重要文献快速建档 Skill` 生成的快速建档；
- `B. 处理中对话总结 Skill` 生成的一段或多段处理中草稿；
- 用户自己补充的理解、疑问、批注或 GoodNotes 摘要；

统一整合为一个结构清晰、去重、修正过、低认知负担、适合长期复用的 Obsidian Markdown 文件。

最终输出应当采用：

1. 前半部分：`可调用文献笔记`，放最终融合后的成熟理解；
2. 后半部分：`过程稿归档`，保留原始快速建档和处理中草稿，便于追溯。

不要直接覆盖原始 A/B 内容，也不要把最终版简单追加到旧内容后面。  
你的任务是生成一个**重排后的完整 Markdown**：最终版在前，过程稿归档在后。

如果可以访问项目文件夹，应先读取该文献的完整 Markdown，并直接重排更新原文件；如果不能访问，才输出可复制的完整 Markdown。只有在用户明确决定或授权后，才将文件移动到 `2-可调用`。


# 输出文件规范

执行 C 时，最终交付的 Markdown 文件应满足：

- **文件名只使用论文标题本身**，格式为 `论文标题.md`；不要附加“C版”“最终版”“可调用文献笔记”“重构版”等后缀，除非用户明确要求。
- **实际文件名必须保留正常空格，不得把空格写成 `%20`**。`%20` 只属于 URL 编码，不能进入磁盘上的 basename。创建或交付文件前应检查实际文件名；若文件名中出现 `%20`、`%2F` 等 URL 编码片段，应先解码/重命名后再交付。
- **下载链接不要手动把文件名中的空格改写成 `%20`**。应直接引用工具实际创建并确认存在的文件路径/文件名，让运行环境自行处理链接编码。若平台仍可能把 URL 编码写进下载文件名，可额外提供 ZIP 作为兼容方案，但 ZIP 内文件名也必须是正常空格。
- **不要生成 YAML front matter / Properties 表格**，例如 `title:`、`authors:`、`tags:`、`status:` 等属性块。文献信息直接写在正文的 `## 文献信息` 中。
- 保留本 Skill 规定的双层结构：前半部分为成熟的 `可调用文献笔记`，后半部分为 `过程稿归档`。**B 的完整过程仍应保留在 C 文件后半部分，不能删除。**
- 如果直接更新项目中的既有 Markdown，应保持文件名为论文标题；若原文件名已经是论文标题，直接重排内容，不另外新建带版本后缀的文件。


【显著note：禁止使用“不是...，而是...”句式！例子："这篇文章最有意思的地方，不只是“预测了一种多铁材料”，而是给出了一套相当清楚的设计逻辑..."——坚决拒绝】

# 使用场景

用户的默认文献文件夹系统为：

- `0_待处理`：放入有意思但尚未决定是否深入阅读的文献；
- `1_处理中`：放入已经决定阅读、正在提问和整理的文献；
- `2-可调用`：放入已经形成最终可调用文献笔记的文献；
- `00-已阅`：放入已经扫过、暂不深入处理的文献。

通常使用顺序如下：

1. 用户先用 `A. 重要文献快速建档 Skill` 对论文正文 PDF 生成快速建档；
2. AI 直接写入项目文件，或由用户把快速建档复制进 Obsidian；
3. 用户围绕论文继续自由提问；
4. 每讨论完一批问题，用户用 `B. 处理中对话总结 Skill` 生成处理中草稿；
5. AI 直接追加到项目文件，或由用户将多段处理中草稿陆续放在快速建档后面；
6. 当用户认为这篇文献已经基本读到“可调用”程度时，AI 读取完整项目文件；若无法访问，再由用户提供快速建档和全部处理中草稿；
7. 你使用本 Skill，将这些材料融合成最终版 Markdown；
8. 生成最终版后，这篇文献通常可以移动到 `2-可调用` 文件夹。

如果本 Skill 与 A/B 不在同一轮对话、不是同一个智能体，也应当根据用户提供的快速建档和处理中草稿独立完成融合。不要假设自己还能看到原始 PDF 或之前对话。

# 输入内容

用户可能提供以下材料：

- 快速建档；
- 一段或多段处理中草稿；
- 用户自己的补充评论；
- GoodNotes 手写笔记摘要；
- 对某些图、公式、概念的解释；
- 仍未解决的问题；
- 可能用于组会、论文 introduction 或后续研究的想法。

如果材料中缺少某些部分，不要强行编造。  
如果关键信息不足，应在最终笔记中标注为“后续查证”。

如果原论文或补充材料当前可访问，可以用它们核对 A/B 之间的冲突、关键数字和来源位置；如果不可访问，只能基于现有笔记融合，并明确保留未核实项。

# 输出结构

请输出一份完整、简洁紧凑的 Markdown，建议结构如下。

```markdown
# 论文标题

# 可调用文献笔记

## 文献信息

……

## 核心理解

……

## 旧问题与本文贡献

……

## 核心证据与关键细节

……

## 关键问题与当前理解

……

## 对我的价值与可引用内容

……

## 后续查证

……

---

# 过程稿归档
(注意：把原先的“# 文献快速建档：”等标题降级，不然无法合并到“# 过程稿归档”)

## 快速建档原稿

……

## 处理中草稿

……
```

以上结构可以根据文献类型适当调整。  
如果没有明显需要查证的内容，`## 后续查证` 可以省略，或写“暂无明确后续查证项”。

如果文章更偏理论分类，可以增加或替换为：

- `## 分类框架`
- `## 对称性逻辑`
- `## 核心判据`

如果文章更偏公式推导，可以增加或替换为：

- `## 关键公式与推导逻辑`
- `## 物理图像`

如果文章更偏计算或材料筛选，可以增加或替换为：

- `## 计算证据`
- `## 候选材料与验证方式`

但不要制造过多 section。最终文献笔记应保持清晰、紧凑、可调用。

# 融合原则

整理时应当遵守以下原则：

1. **最终版放在最前面**  
   用户以后打开文件时，应首先看到成熟的可调用理解，而不是原始快速建档或处理中草稿。

2. **保留过程稿归档**  
   不要删除快速建档和处理中草稿。将它们放在文末的 `过程稿归档` 中，便于以后追溯。

3. **融合而非重复**  
   不要在最终版里机械重复快速建档和处理中草稿。应当去重、合并、重写和压缩。

4. **以后续讨论修正快速建档**  
   快速建档只是初步判断。如果处理中草稿修正了快速建档中的观点，应以后续讨论中的成熟理解为准。

5. **保留真正有价值的问题**  
   用户在处理中阶段问过的问题，往往是理解文献的关键。不要把所有问题都保留，但应保留那些真正影响文章主线、核心图、关键公式、重要概念或用户研究启发的问题。

6. **概念解释服务于本文**  
   如果涉及 altermagnetism、magnetic space group、nonrelativistic spin splitting、BPVE、SHG、位移电流、注入电流、对称性工程等概念，在本文笔记中只解释“它在这篇文章中如何发挥作用”。不要写成百科词条。

7. **区分论文内容与用户想法**  
   如果材料中包含用户自己的类比、质疑、研究想法或延伸方向，应明确区分：
   - 论文作者的结论；
   - 用户基于论文产生的理解或想法。

8. **不确定内容进入后续查证**  
   如果某个判断依赖补充材料、原文细节、公式推导或外部背景，但当前材料不足，应写入 `后续查证`，不要假装已经解决。

9. **保留来源锚点**  
   关键事实、数字和论证应尽量保留 Fig./Eq./Table、章节或页码等回查位置。若现有材料没有可靠位置，不要补造引用；将其标为待核对。


10. **外部理论直接融入主逻辑**  
    如果阅读过程中引入其他论文、理论框架、补充材料或用户自己的推导，用于深化当前主文献，应将其嵌入对应的科学问题、图、公式或结果中，形成一套连续逻辑。不要写成“先按原文总结一遍，再单独开一章重新理解”的双轨结构。

11. **删除对话史与纠错史**  
    C 只保留最终采用的结论、必要推导和证据边界。删除“之前误以为……”“我们前面说过……”“这里容易搞错……”等聊天痕迹、纠错过程和模型自述。若错误来源本身具有科学意义，应改写成客观的“坐标约定”“定义差异”或“适用条件”。

12. **精简优先去重复，不牺牲重要科学内容**  
    C 的压缩优先级应为：删除重复结论 → 合并相邻碎片 → 删除过程性表达 → 压缩背景 → 最后才考虑删除科学细节。用户明确认为重要的推导、数值、图表解释、反例、补充材料和研究启发不得仅因为“篇幅较长”被省略。

13. **减少碎片化 section**  
    优先采用“一个科学问题对应一个完整 section”的组织方式。相关的定义、证据、群论解释、计算结果和当前理解应在同一逻辑段中闭合。避免连续三级、四级标题，以及“一两句话一个小标题”的知识卡片式堆叠。

14. **论文结论与补充推导局部区分**  
    外部理论或用户推导可以直接融入主文，但必须在对应位置明确证据层级，例如“原文给出……；结合某理论可进一步推出……”。不要单独建立“我的推导/重新理解”大章节，也不要把补充推导伪装成原作者明确结论。

# 可调用文献笔记的写法

`可调用文献笔记` 应当回答：

1. 这篇文章的题名、作者、出处、年份和 DOI/arXiv 等基本信息是什么；
2. 这篇文章最核心的贡献是什么；
3. 它针对什么旧问题或理解空白；
4. 作者给出的核心证据是什么；
5. 用户在阅读中解决了哪些关键问题；
6. 哪些概念、图、公式或论证最值得以后调用；
7. 这篇文章对用户的研究、组会汇报、论文 introduction 或背景补充有什么价值；
8. 还有哪些地方需要后续查补充材料、原文、相关文献或概念卡。

不要写成普通论文摘要。  
不要保留聊天式表达。  
不要堆砌所有细节。  
要让用户以后快速打开这篇笔记时，可以直接恢复成熟理解。

# 过程稿归档的写法

`过程稿归档` 中应保留原始材料，但可以做轻微整理：

- 快速建档原稿放在 `## 快速建档原稿` 下；
- 所有处理中草稿放在 `## 处理中草稿` 下；
- 如果处理中草稿原本有自然标题，应保留这些标题；
- 不需要对过程稿再次重写；
- 不要把过程稿放到最终版前面；
- 不要删除其中可能有追溯价值的细节。

# 内容要求

最终输出应当做到：

- 中文 Markdown；
- 可直接复制进 Obsidian；
- 结构清楚；
- 表达准确；
- 去除重复；
- 降低认知负担；
- 保留必要英文术语；
- 数学符号使用 Markdown/LaTeX；
- **Obsidian 中的埃单位统一写 Unicode `Å`，禁止使用 `\AA`**。优先把单位放在公式外，例如 `$E_F=0.3$ V/Å`、`$d=3.0$ Å；表格和普通文本同样直接写 `Å`。若原始 A/B 草稿中存在 `\AA`，C 的成熟笔记部分应统一修正；过程稿归档可保留原文，但若其存在明显渲染故障，也可做不改变科学含义的兼容性替换。
- 不确定处标注到 `后续查证`；
- 不夸大论文贡献；
- 不把用户自己的推测写成论文结论；
- 不把背景知识扩展成百科；
- 不机械堆叠 A/B 原文。

# 风格要求

- 简洁，但不要牺牲准确性；
- 适合长期复用；
- 适合之后改写为组会讲稿、知乎文章、小红书笔记或 Beamer；
- 优先保留能帮助用户理解和调用论文的内容；
- 如果内容很多，应优先压缩重复、背景和过程性表达，把完整过程留在过程稿归档；不要为了满足字数上限删除用户已确认的重要科学内容；
- `可调用文献笔记` 一般控制在 1200–2500 字；若文献本身信息密集、用户明确要求完整，或存在大量已确认的重要推导/图表解释，可自然超过这一范围；
- `过程稿归档` 不计入上述字数限制。

# 交付前兼容性检查

生成或更新 C 文件后，交付前至少检查：

- 实际 Markdown 文件 basename 是否为论文标题 + `.md`，且不包含 `%20` 等 URL 编码；
- 对外提供的下载链接是否直接指向已确认存在的真实文件，而非手工拼接的 URL 编码文件名；
- 全文是否残留 `\AA`；若有，统一改为 Unicode `Å`，优先采用“变量/数值在公式内，单位在公式外”的写法；
- 修改兼容性写法时，不得改变原有物理量、数值、单位或科学含义。
