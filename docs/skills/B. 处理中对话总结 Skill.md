# 目标

当用户围绕一篇文献连续提出若干具体问题后，你的任务是将**当前对话中最近一段尚未整理过的文献讨论**整理成一段**可直接写入或复制进 Obsidian 的处理中草稿**。

通常使用顺序如下：

1. 用户先发送 `A. 重要文献快速建档 Skill` 和文献正文 PDF，生成快速建档；
2. AI 直接写入项目文件，或由用户将快速建档复制到 Obsidian 的该文献 Markdown 中；
3. 用户继续在同一对话框中围绕这篇文献自由提问；
4. 当一批问题讨论结束后，用户发送本 Skill；
5. 你基于当前对话上下文，将这批尚未整理过的讨论整理成处理中草稿；
6. AI 直接追加到项目文件，或由用户将这段处理中草稿复制到快速建档内容后面（需要你给出 markdown 代码块，注意公式渲染等格式问题。不要过多换行。）；
7. 后续可以继续在同一对话框中提问，再次发送本 Skill；
8. 第二次及之后使用本 Skill 时，默认只总结“上一次处理中草稿之后，到本次发送 Skill 之前”的新讨论内容，不要重复总结已经整理过的内容；
9. 最后再由最终文献笔记融合 Skill 将快速建档和多段处理中草稿融合成可调用文献笔记。

如果可以访问项目文件夹，应先读取该文献现有 Markdown，确认哪些讨论已经整理，再把本次草稿直接追加到唯一的 `# 处理中草稿` 部分。第一次写入时创建该部分；后续不要重复创建同名一级标题。如果不能访问项目文件，才输出可复制的 Markdown 片段。

这里的“处理中草稿”不是最终文献笔记，也不是完整报告，而是把用户和 AI 的零散讨论压缩成清晰、准确、低认知负担、可复用的 Markdown 草稿。它应当放在该文献快速建档内容的后面，作为后续生成最终可调用文献笔记的中间材料。本 Skill 只整理用户在本轮讨论中真正问过、卡住过、推进过的内容。不要为了完整而补写整篇文章背景，也不要主动扩展到用户没有问、且不影响本文理解的内容。

用户的问题可能很零散，可能涉及：

- 某段英文原文的理解；
- 某张图、某个公式、某个表格；
- 某个陌生概念或背景知识；
- 作者的论证逻辑；
- 论文和用户研究方向的关系；
- 用户自己的疑问、反驳、类比或想法。

不要强行套固定模板。重点是把本轮讨论中真正有价值的内容整理清楚，让用户不需要重新回看长对话，也能快速恢复这一段讨论的核心理解。

如果当前对话上下文足够，应直接总结，不要要求用户重新粘贴讨论内容。  
在同一个任务中，以“上一次 B 输出”为边界；跨任务时，以文献 Markdown 中已有的 B 草稿和用户本次提供的新讨论为边界，不要假设自己能看到过去的聊天。  
如果无法判断边界，但能识别最近一段明显尚未整理过的讨论，可以先总结，并用一句话或隐藏注释说明本次整理范围；如果仍然无法可靠判断，则明确说明需要用户补充相关问答或指定范围，不要猜测。

# 输出原则

输出应当满足：

1. 中文 Markdown；
2. 【回答应当忠实原文，以原文为最主要依据】
3. 【注意，应当先把用户的问题精确、简洁地复述或重述一遍，再对此进行点对点的回答。】
4. 可直接复制进 Obsidian；
5. 不使用“讨论总结 1 / 讨论总结 2”这类有序标题；
6. 标题应根据本轮讨论内容自然生成，例如：
   - `## Fig. 1 的分类逻辑`
   - `## 关于 nonrelativistic spin splitting 的理解`
   - `## Introduction 中研究动机的梳理`
   - `## 零散问题整理`
5. 默认只总结上一次处理中草稿之后的新讨论，不重复整理已经总结过的内容；
6. 不需要判断“是否进入最终报告”；
7. 不需要判断“是否需要独立概念卡”；
8. 不要重复快速建档中已经写清楚的泛泛内容；
9. 优先整理用户真正问过、讨论过、卡住过的内容；
10. 遇到不确定的地方，明确标注“后续查证”；
11. 写得简洁，但不能牺牲准确性；
12. 目标是降低用户认知负担，而不是制造新的整理负担；
13. 关键图、公式、数字和原文结论尽量保留 Fig./Eq./Table、章节或页码等回查位置；没有依据时不要补造位置。

# 输出格式

请根据本轮讨论内容选择合适结构。不要机械套用所有小标题。

每段 B 草稿建议以隐藏注释记录整理日期和范围，便于跨任务去重；如果日期或范围无法确认，可省略对应字段：

```markdown
<!-- B-SUMMARY: YYYY-MM-DD | 范围：一句话说明 -->
```

这个注释只用于过程追踪，不替代自然主题标题。

常用格式（注意简洁紧凑）如下：

```markdown
<!-- B-SUMMARY: YYYY-MM-DD | 范围：一句话说明 -->

## 本轮讨论的自然主题标题

### 主要问题

- ……
- ……
- ……

### 当前理解

- ……
- ……
- ……

### 对理解本文的帮助

……

### 后续查证

- ……
```

如果本轮讨论非常零散，可以使用如下格式：

```markdown
## 零散问题整理

### 问题：……

回答：……

### 问题：……

回答：……

### 问题：……

回答：……

### 小结

……
```

如果本轮讨论集中在一张图，可以使用如下格式：

```markdown
## Fig. X 的理解

### 这张图想说明什么

……

### 关键 panel / 坐标 / 符号

- panel a：
- panel b：
- panel c：

### 它和正文主线的关系

……

### 仍需确认

……
```

如果本轮讨论集中在一个公式，可以使用如下格式：

```markdown
## Eq. X 的理解

### 公式在文章中的作用

……

### 符号与物理含义

- `$...$`：
- `$...$`：

### 推导或逻辑关系

……

### 仍需确认

……
```

如果本轮讨论集中在一个概念，可以使用如下格式：

```markdown
## 关于某概念的理解

### 在本文中的含义

……

### 它和相近概念的区别

……

### 它为什么重要

……

### 仍需确认

……
```

如果本轮讨论没有明显单一主题，可以不用强行归类，直接按问题组织：

```markdown
## 零散问题整理

### 问题：……

……

### 问题：……

……

### 问题：……

……

### 小结

……
```

# 内容要求

整理时应当做到：

- 不要把聊天过程逐字复述；
- 不要把 AI 原回答原样堆进去；
- 不要为了完整而保留无关细节；
- 不要写成百科词条；
- 不要扩展到用户没有问、且和本文理解关系不大的内容；
- 不要重复已经在前一次处理中草稿里整理过的内容；
- 如果用户的问题中有误解，应在总结中自然修正；
- 如果本轮讨论推翻或修正了快速建档中的某个初步判断，要明确指出；
- 如果本轮讨论只是补充细节，不要重新概括整篇文章；
- 如果本轮讨论包含多个互不相关的小问题，可以用“零散问题整理”的形式分条总结；
- 如果本轮讨论包含用户自己的想法、类比或质疑，应保留其中有价值的部分，并和论文内容区分清楚；
- 如果某个问题尚未得到可靠回答，应写为“后续查证”，不要假装已经解决；
- 如果某个解释只是为了帮助理解本文，不要展开成过长的背景介绍。

# 降低认知负担的要求

输出应当尽量做到：

- 让用户不需要重新阅读长对话；
- 直接给出结论，而不是复述推理过程；
- 用短句和清晰项目符号表达；
- 把零散问答合并成少数几个清楚的理解点；
- 删除无关铺垫、客套话和重复解释；
- 对复杂概念先给一句“最短理解”，再给必要补充；
- 对图、公式、概念分别说明“它在本文中起什么作用”；
- 对不确定内容明确标注，不增加用户判断负担；
- 如果内容太多，优先保留最影响理解本文主线的部分。

# 风格要求

- 语言简洁、清楚、准确；
- 适合以后被整合进最终文献笔记；
- 尽量使用短段落和项目符号；
- 保留必要的英文术语；
- 数学符号使用 Markdown/LaTeX 格式；
- 不要使用夸张表达；
- 不要写“本轮讨论很有价值”之类的空话；
- 一般控制在 300–800 字，除非用户明确要求更详细。
