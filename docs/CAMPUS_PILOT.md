# Literature Agent 校内试点基线

> 状态：已批准推进
>
> 首轮范围：课题组 / 班级群邀请制试点
>
> 周期：4 周
>
> 建议规模：20–30 人

## 1. 试点目标

验证一件事：系统能否持续理解不同用户的研究项目，并每天交付少量、真正值得看的论文。

本阶段不以论文总量、抓取来源数量或完整 APP 为成功标准。成功标准是：

- 用户可在 10 分钟内完成初始研究画像；
- 每日推荐数量受控，默认不超过用户设置的注意力预算；
- 用户认为有用的推荐比例持续提高；
- 用户能够完成“发现 → 判断 → 深读 → 回查”的闭环；
- 单用户月成本可测量、可限制；
- 不依赖共享机构账号或集中下载订阅全文。

## 2. 产品边界

### 2.1 产品负责

- 聚合公开论文元数据、摘要和合法开放全文；
- 建立每位用户独立的研究画像；
- 按 `MUST / WEEKLY / RADAR / DROP` 推荐；
- 生成每日文献列表和重点论文 A 建档；
- 接收 `read / later / ignore` 决定与附加标记；
- 保存用户自己的笔记、反馈和私有上传文件；
- 导出到 Zotero、Obsidian 或标准文件格式。

### 2.2 产品暂不负责

- 使用校园 IP、统一认证账号或代理集中下载订阅论文；
- 在用户之间共享受限 PDF；
- 替代 Zotero 做完整参考文献管理；
- 替代 Obsidian 做通用知识库；
- 在首轮试点开发原生 iOS / Android 客户端；
- 承诺无限 AI 深读。

## 3. 首次使用流程

1. 用户通过邀请码创建账户。
2. 创建 1–3 个研究项目，每个项目输入 100–500 字说明。
3. 通过 DOI、标题、BibTeX/RIS 或 Zotero 导入 10–30 篇种子论文。
4. 系统生成初始研究画像，用户确认或修改。
5. 用户设置每日注意力预算、通知时间和语言。
6. 系统开始每日推荐；用户通过反馈持续修正画像。

### 3.1 必填输入

- 账户与邀请码；
- 至少一个研究项目；
- 至少 5 篇种子论文，建议 10–30 篇；
- 每日推荐上限；
- 对推荐结果的基本反馈。

### 3.2 可选输入

- Zotero 指定 Collection；
- BibTeX / RIS 文件；
- 自定义公开 RSS；
- 关注作者、期刊、关键词和排除主题；
- 用户合法取得的 PDF；
- 用户自己的模型 API；
- Obsidian 导出设置。

### 3.3 永不收集

- 清华统一认证密码、VPN 密码或 Cookie；
- 出版商账号密码；
- 与推荐无关的未公开实验数据；
- 未经用户选择的完整 Zotero 文献库；
- 用于跨用户共享的订阅 PDF。

## 4. 全文获取链路

全文解析严格按以下顺序进行：

1. 开放获取版本：arXiv、机构仓储、PMC、Unpaywall 等；
2. 出版商公开全文；
3. DOI / 出版商页面，并提示用户通过自己的机构权限访问；
4. 用户手工下载后上传到自己的私有空间；
5. 无法取得时标记 `blocked_pdf`，不得伪造已读全文。

清华订阅可降低具备权限用户的个人阅读成本，但不作为平台公共全文库。平台只保存用户明确上传到私有空间的文件，并提供删除和导出能力。

## 5. 试点版功能范围

### P0：必须交付

- 邀请码注册与用户隔离；
- 研究项目和研究画像；
- DOI / 标题 / BibTeX / RIS 种子导入；
- 每用户独立的推荐分级；
- 每日网页总览；
- `read / later / ignore` 与推荐反馈；
- OA 优先的全文获取状态；
- 私有 PDF 上传；
- A 建档任务与月度额度；
- 数据导出和账户删除；
- 管理端成本、错误和来源健康统计。

### P1：试点中追加

- Zotero 官方授权连接；
- 邮件通知；
- Obsidian Markdown 导出；
- 导师 / 课程共享阅读清单，只共享元数据和笔记；
- 推荐原因和画像调整入口。

### P2：验证后再决定

- 原生 APP；
- 机构统一登录；
- 付费套餐；
- 课题组管理后台；
- 出版商或图书馆正式合作接口；
- B / C / D 全流程网页化。

## 6. 多用户数据边界

现有个人版的 `collect → dedup → screen → process → A queue → overview` 继续作为稳定内核。产品层新增多用户边界：

| 数据 | 隔离方式 |
|---|---|
| 公共论文元数据 | 全局共享，论文级去重 |
| 来源运行状态 | 全局共享 |
| 用户账户 | 用户私有 |
| 研究项目与画像 | 用户私有 |
| 推荐结果与反馈 | 用户 × 项目私有 |
| 上传 PDF | 用户私有，不跨用户展示 |
| A/B/C/D 笔记 | 用户私有；主动分享时另建授权记录 |
| AI 密钥 | 加密保存，可撤销，不进入日志 |

推荐优先级仍只允许 `MUST / WEEKLY / RADAR / DROP`；A/B/C/D 继续表示阅读工作流，不得合并为一条状态轴。

## 7. 技术演进原则

首轮采用 Web 产品，保留 Python 内核：

```text
Web 前台
  → 产品 API（账户、项目、推荐、反馈、额度）
  → 任务队列
  → 现有 Python 文献内核
  → PostgreSQL + 私有对象存储
```

实施时遵循：

- 个人版继续可独立运行，不因产品化停止；
- 先把领域逻辑从本机路径和全局单例中抽离，再接 Web；
- 公共论文事实与用户私有判断分表；
- 所有后台任务幂等，可重试并记录审计事件；
- 本地 SQLite 保留用于个人版和测试，服务端使用 PostgreSQL；
- Obsidian / Zotero 通过适配器连接，不进入核心数据模型。

## 8. 四周里程碑

### 第 1 周：多用户基础

- [x] 明确服务端数据模型；
- [x] 抽离用户、项目、画像和种子论文接口；
- [x] 建立账户隔离和最小权限测试；
- [x] 建立单用户成本计量字段；
- [x] 用显式已确认画像生成项目级推荐，并保存画像修订号；
- [x] 固化最小应用服务契约；HTTP 登录与路由进入下一阶段。

验收：两个测试用户使用同一篇种子论文，能共享公共元数据，但互相看不到项目、反馈、PDF 和笔记。

状态：已通过自动化验收。同一批公共论文可按不同项目输出不同优先级；重复运行幂等；跨用户项目、画像、推荐与私有资产访问被调用层和数据库层共同拒绝。

### 第 2 周：每日推荐闭环

- 接入现有采集与去重内核；
- 生成每用户推荐；
- 完成网页每日总览；
- 支持 read / later / ignore 和画像反馈。

验收：用户从注册到收到第一份推荐无需配置本地路径、Obsidian 或 Zotero。

### 第 3 周：全文与 A 建档

- 实现 OA 优先解析；
- 实现私有 PDF 上传；
- 实现机构访问跳转；
- 接入 A 建档队列、额度和成本记录。

验收：没有全文时如实标记；一个用户上传的 PDF 对其他用户不可见；额度耗尽后不会继续产生平台模型费用。

### 第 4 周：邀请试点

- 邀请 20–30 名用户；
- 增加错误监控、备份、数据导出和删除；
- 每周收集一次访谈与量化反馈；
- 输出继续、调整或停止的试点评估报告。

## 9. 预算护栏

首轮建议：

- 固定基础设施上限：¥300/月；
- 平台 AI 总预算上限：¥1,000/月；
- 每位用户默认 5 篇完整 A 建档/月；
- 日常标题与摘要筛选设置合理使用上限；
- 超额时暂停完整 A，允许用户连接自己的 API；
- 每个模型调用记录用户、任务、输入/输出量、估算成本和状态。

任何需要提高预算上限的改动，应先用试点数据说明：有用推荐率、留存、A 使用率和单位成本。

## 10. 试点指标与继续条件

### 核心指标

- 激活率：完成项目和种子论文导入的注册用户比例；
- 首次价值时间：注册到看到第一份有效推荐的时间；
- 有用推荐率：`read + later` 占已决定推荐的比例；
- MUST 精确率：用户接受的 MUST 占比；
- 周留存：一周内至少处理一次推荐的用户比例；
- A 使用率与完成率；
- 单活跃用户月成本；
- OA / 机构跳转 / 用户上传 / blocked 的全文来源占比；
- 数据隔离或版权事故数，目标为 0。

### 建议继续条件

四周结束时，同时满足以下多数条件再扩大范围：

- 至少 15 名完成激活的真实用户；
- 周留存达到 50% 以上；
- 已决定推荐的有用率达到 50% 以上；
- 用户能明确描述系统节省的检索或筛选时间；
- 单活跃用户月成本处于可接受范围；
- 无跨用户数据泄露和机构资源违规事件。
